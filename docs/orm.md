# Database access: an ORM

## Decision record

### Context

NestJS has to create shopkeepers and shops, list products, and accept an export. PostgreSQL only runs SQL. The assignment allows Sequelize, TypeORM, or Prisma. The accept path has to be something we can explain: the request and the quantities change together, or not at all.

### Problem

Decide how the NestJS service talks to PostgreSQL: hand-written SQL, or a library that turns TypeScript models into SQL and keeps migrations.

### Options considered

**Hand-written SQL through the `pg` driver.** The service sends SQL strings. The accept transaction is visible line by line. Repetitive inserts and selects are written by hand. Table changes are SQL migration files the team maintains.

**An ORM.** The tables are described in code or in a schema file. The library generates the SQL for ordinary reads and writes and tracks migrations so the database stays aligned with the model.

Within ORMs, three were compared in detail:

1. **Prisma.** One `schema.prisma` file describes the models. A generate step builds a typed client. Queries read like `findMany` and `create`.
2. **Drizzle.** Tables are TypeScript. Queries are written in a form close to SQL. Migrations are SQL files you can open.
3. **TypeORM.** A class per table, with decorators, injected like other NestJS services. This is the integration NestJS documents first.

Sequelize is on the assignment's allowed list. It was not given the same comparison. It should not be introduced later without that comparison.

### Decision

Use **Prisma** 7.10.0.

The only migration is [backend/prisma/migrations/20261007063300_init/migration.sql](../backend/prisma/migrations/20261007063300_init/migration.sql). Prisma applies it. There is no second SQL folder.

Prisma 8 is only a release candidate, so it was not used.

### Reasons

Prisma keeps the market's data in one `schema.prisma` file: shopkeeper, shop, product, and transfer request, including `unitPrice` and the stored `totalPrice`. That is the same kind of readable structure we wanted from Next.js and NestJS.

Drizzle would have kept the SQL more visible. The race rules are already visible in the SQL functions, so Prisma does not hide the accept path. TypeORM's usual `save()` loads a row and writes it back, which is the unsafe accept. Prisma is not chosen because it has the most features. It is chosen because the model file matches the ER diagram and the assignment already lists it.

### Trade-offs

- Prisma Client does not know the check constraints or the triggers. Those stay in the SQL migration. A later `prisma migrate dev` must be read before it is applied, so it does not drop a check it cannot see.
- Accepting a transfer is `accept_transfer_request()` in PostgreSQL, called from NestJS. A Prisma `update` that loads the row and then saves it can still lose the race. `updateMany` where status is still `pending`, and a check that one row changed, is the safe Prisma shape if we ever stop using the function.
- `totalPrice` is generated by PostgreSQL. Prisma reads it and does not set it.
- `prisma generate` has to run inside the backend image when that container is added. It is not part of the current Postgres-only Compose file.
- Sequelize was on the assignment list and was not compared. It stays out unless that comparison happens.

### Consequences

- The Prisma schema is [backend/prisma/schema.prisma](../backend/prisma/schema.prisma). The database URL is `DATABASE_URL` in `backend/.env`, which is not committed.
- The next schema change is a new Prisma migration, not an edit to the init SQL that already ran.
- Shop, product, and request reads go through Prisma Client. Publish, accept, and cancel go through the existing SQL functions so the row locks stay in one place.

## schema.prisma and migration.sql

They are related, and they are not the same description written twice.

[schema.prisma](../backend/prisma/schema.prisma) is the model Prisma Client uses from TypeScript. It lists Shopkeeper, Shop, Product, and TransferRequest, their columns, their relations, and a few indexes. The field names are camelCase. `@@map` and `@map` point each one at the snake_case table and column in PostgreSQL. `totalPrice` is marked `dbgenerated`, which means PostgreSQL fills that column and Prisma only reads it.

[migration.sql](../backend/prisma/migrations/20261007063300_init/migration.sql) is the script PostgreSQL executes. Prisma records that this script has been applied, in its own `_prisma_migrations` table. `npx prisma migrate deploy` is what applied it to the empty database.

On a later change, `prisma migrate dev` can generate a new `migration.sql` by diffing `schema.prisma` against the database. In that ordinary case, the migration is the PostgreSQL form of the schema change: create a column, add an index, and so on.

This first file was not produced that way. The SQL was written so the database could enforce rules the schema file cannot store:

- check constraints, such as a unit price above zero and a source shop different from the destination
- the `open_transfer_board` view
- triggers that keep pending quantities inside the shelf quantity
- `create_transfer_request`, `accept_transfer_request`, and `cancel_transfer_request`

`schema.prisma` was then lined up with the four tables that SQL created. A diff from the live database back to the schema file was empty, which means the columns match. The checks, the view, and the functions stay only in the SQL.

Reads use the schema file through Prisma Client. Publish, accept, and cancel use the functions in the migration. A generated migration from a schema edit must be read before it is applied, because Prisma can propose dropping a check it does not know about.

## Technology note

1. **What it is.** An object-relational mapper turns table rows into values in the programming language and writes the SQL for you.
2. **What problem it solves.** It bridges TypeScript and PostgreSQL for ordinary queries and keeps a migration history. It does not invent the transfer rules.
3. **What alternatives exist.** The `pg` driver with SQL we write. Inside ORMs: Prisma, Drizzle, TypeORM, and the not-yet-compared Sequelize.
4. **What VMarket requires.** Shopkeeper, shop, product, and transfer-request persistence, plus a transaction on accept.
5. **Why it was selected.** Prisma's schema file is the readable model of the four tables, and the assignment already allows Prisma. The transfer race stays in SQL functions that Prisma does not replace.
6. **What trade-offs it introduces.** A generate step, a client that does not see check constraints, and a rule that accept is not a normal Prisma update. The migration file is the database script. It is not a printout of `schema.prisma`.

## Prisma, Drizzle, and TypeORM

| Concern | Prisma | Drizzle | TypeORM |
|---|---|---|---|
| Where the model is | One schema file. Closest thing to a readable ER diagram. | TypeScript table definitions. | Entity classes spread across modules. |
| Everyday product list | Short method calls. | A select / from / where that resembles SQL. | A repository `find`. Comfortable in NestJS. |
| TypeScript | Strong after generate. | Strong without a generate step. | Entity types are fine. Some query results are loose. |
| Safe accept update | `updateMany` where status is pending, then check the count. `find` then `update` is unsafe and is what tutorials show first. | The `where status is pending` clause is the normal way to write the update. | Possible in the query builder. `save()` is the unsafe default habit. |
| Migrations | Guided. Do not edit the live database. | A SQL file you can diff against the ER diagram. | Exists, and is easier to bypass with synchronize. |
| NestJS fit | A small injectable `PrismaService` you write once. | A small injectable client. Fewer official NestJS examples. | First-party `@nestjs/typeorm` package. |
| Docker | Generate the client inside the Linux image. | JavaScript only. | JavaScript only. |
| First week | Easiest of the three, if the accept lesson is taught on purpose. | More SQL up front, less translation later. | Decorators feel familiar, then `save()` surprises you. |

### Lean that was chosen

Prisma. Drizzle would have been the choice if the priority had been reading every query as SQL in TypeScript. TypeORM was not chosen, because `save()` is the wrong habit for accept.
